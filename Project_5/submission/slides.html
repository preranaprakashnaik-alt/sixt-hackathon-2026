The model reads.
The code calculates.

Trustworthy answers to business questions with a 31B open-weight model

The problem

"What was net revenue?" hides a dozen rules: which orders count, which exchange rate, how discounts and refunds are split. One slip gives a confident wrong number.

Our idea

Let a small model do what it is good at: understanding the question. Let tested code do what must be exact: applying the rules and the arithmetic.

Result so far

All 200 Stage 1 questions answered. 10 of 10 organizer-solved examples reproduced exactly.

How it works

One question, five steps. The model never sees data rows and never does arithmetic on the main path.

1. Question"What was net revenue from customers in Spain in Q2 2024?"
➜
2. Gemma 4 31B routes{"recipe": "net_revenue", "params": {"country": "Spain", "period": "Q2"}}
➜
3. ValidatorRecipe exists? Values exist in the data? If not, ask again.
➜
4. Tested code70 recipes on a verified data layer where every business rule is applied once.
➜
5. Answer CSVFormatted once: two decimals, exact counts, dates, true/false.

Verified data layer

  • Valid orders, resolved customer identities
  • Monthly exchange rates, discount and refund allocation
  • Late shipments, service-level breaches, reconciled stock
  • Stops with an error if an assumption breaks

Two engines for the hard 50

  • Exact optimizer for the fulfilment decision cases
  • Step-by-step simulator for the warehouse event cases
  • Both with counterfactual mode

When no recipe fits

  • Gemma says "no matching recipe"
  • Gemma writes the calculation as code on the verified tables
  • Three independent attempts; accepted only if results agree

The answer key is private, so we built evidence from independent checks. Our own checks, not official feedback.

Built-in guards

  • Joins declare expected cardinality; keys asserted unique
  • Refunds must sum to the eligible total: each counted once
  • Missing exchange rate is an error, never 1

What we do not know

  • Our real accuracy on the 200 scored questions
  • The 20 simulation answers have no independent check
  • Agreement between two implementations is not proof

What Gemma does

  • Understands each question and picks the calculation and its parameters
  • Writes the calculation itself when no recipe fits
  • Maps renamed columns for a new dataset

What we learned

  • The gateway replays identical requests, so "three votes" were really two. We now shuffle the batches to make votes independent.
  • A shared rate limit pushed us to route 20 questions per call.

Disclosure

The pipeline code was written with an AI coding assistant, approved by the organizer and listed in our model declaration. It does not run in the pipeline.

Why SIXT could use this

Define a metric once as tested code. Then anyone can ask for it in plain language.

Business value

  • Trustworthy: every number comes from versioned, tested code
  • Auditable: each answer records which calculation and parameters produced it
  • Cheap: a small model, under 1,000 tokens per question
  • Replaceable: swap the model without changing any result

Honest limits

  • The recipe library was built around the question types we saw
  • The code-writing fallback is less reliable than a tested recipe, and was measured on questions whose hard parts the data layer already solves
  • A new optimization or simulation task still needs hand-written code

Next steps

  • Run the same pipeline on the final stage: new rules, renamed columns
  • Second independent implementation of the hardest metrics
  • Test the fallback on questions that need new base tables
  • Method report as an arXiv manuscript with the organizers
